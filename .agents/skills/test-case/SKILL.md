# 测试用例规范技能（Test Case Specification Protocol）

本技能用于生成**结构化、可追踪、可执行、可审计**的测试用例文档。

它充当：
- QA 架构师
- 测试策略设计师
- 风险控制分析师

它不负责：
- 编写具体业务代码
- 重构系统
- 优化性能（除非属于测试目标）

目标：
让测试成为可度量的工程资产，而非临时验证。

---

# 0. 输出文件（必须）

优先级规则（MUST）：

1. 若请求或上下文明确到某一阶段（如 `P1.phase3`），必须输出到分阶段文件：  
   `docs/project_control/TEST_CASE_SPEC_<phase>.md`（示例：`TEST_CASE_SPEC_P1.phase3.md`）。
2. 仅当用户明确要求“汇总总表”或项目尚未采用分阶段文件时，才写入：  
   `docs/project_control/TEST_CASE_SPEC.md`。
3. 若同时存在总表与分阶段文件，分阶段文件为该阶段真源；总表只保留索引或镜像，不得先写总表再补阶段文件。

可选输出：

- `docs/test_cases/<level>/<filename>.md`

# 4. 测试生成流程

当使用本技能时必须执行：

1. 读取需求文档（PRD）
2. 读取验收规范（docs/project_control/ACCEPTANCE.md）
3. 建立需求 → 测试映射矩阵
4. 识别关键风险点
5. 生成覆盖矩阵：
   - 正常流
   - 异常流
   - 边界值
   - 并发情况（如适用）

# 5. 质量门禁对齐规则

测试必须支持 QA Gate：

- 所有 P0 用例必须存在
- 每个需求至少 1 个测试用例
- 关键路径必须包含集成测试
- 所有异常分支必须有测试

## 5.1 核心能力真实验证规则（新增，MUST）

当测试目标涉及以下核心能力时，必须使用真实依赖执行验证，禁止任何降级或模拟：

- Redis 访问（读写、过期、幂等键、队列/流）
- 数据库访问（真实连接、真实事务、真实约束）
- AI 大模型处理（真实模型接口、真实响应结构、真实超时/错误处理）
- 消息中间件/外部 API（若属于该需求关键路径）

强制要求：

- 不允许使用 mock/stub/fake/in-memory 替代核心依赖。
- 不允许“主路径失败后自动切换模拟数据”并仍判定通过。
- 不允许把“降级路径成功”作为核心验收通过证据。
- 若真实依赖不可用，测试结论必须是 `BLOCKED` 或 `FAILED`，不得标记为通过。

## 5.2 测试用例元数据增强（新增，MUST）

所有涉及核心能力的测试用例，Frontmatter 必须新增：

- `execution_mode: real`（固定值）
- `allow_mock: false`（固定值）
- `critical_dependencies:`（列出 Redis/DB/LLM 等）
- `evidence:`（日志、请求ID、事务ID、trace_id 等证据路径）

示例：

```yaml
execution_mode: real
allow_mock: false
critical_dependencies: [redis, mysql, llm]
evidence:
  - logs/test_run_2026-02-18.log
  - reports/llm_request_ids.json
```

## 5.3 环境阻断与失败输出（新增，MUST）

若执行前检查发现核心依赖不可达（连接失败、鉴权失败、配额不足、DNS 错误等）：

1. 立即停止该用例执行；
2. 输出阻断原因与缺失依赖；
3. 标记为 `BLOCKED`；
4. 不允许自动切换 mock 数据继续执行。

测试报告必须明确区分：

- `FAILED`：在真实依赖可用前提下，行为不符合预期；
- `BLOCKED`：真实依赖不可用，无法完成有效验证。

## 5.4 数据库测试设计强约束（新增，MUST）

当测试用例包含数据库验证时，必须满足：

1. 默认目标库为 `stock_data_test`（除非需求文档明确指定其他测试库）。
2. 设计前必须阅读 `docs/architecture/*.sql`，并在用例中引用真实表/字段/约束。
3. 禁止基于自建简化表结构给出“通过”结论。
4. 优先复用项目现有数据库测试基线（优先参考 `database_service/scripts/test_theme_processor.py` 及现有 `database_service/tests/**` fixture）。
5. 用例中必须写明“验证真实表结构一致性”的检查点（如 `financial_categories/theme_master` 存在性与关键字段约束）。

## 5.5 先失败证据质量规则（新增，MUST）

`TDD` 的“先失败”证据必须是目标 `TC-ID` 的行为断言失败，不接受以下伪证据：

- 仅凭 DNS/网络故障导致的执行失败；
- 仅凭依赖未启动导致的连接失败；
- 人工写入“expected failure observed”但测试实际通过。

---

# 6. 禁止行为

本技能不得：

- 使用模糊语言（如“正常工作”）
- 省略失败判定
- 省略前置条件
- 生成不可复现步骤
- 对核心链路使用 mock/stub/fake 替代真实依赖
- 在核心测试中启用自动降级并仍给出“通过”结论
- 将“本地模拟通过”表述为“需求已验收”

---

# 7. 行为特征

必须：

- 严谨
- 可追溯
- 可度量
- 风险优先
- 非乐观表达
