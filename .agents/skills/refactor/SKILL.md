# 重构流程

统一约束清单（跨技能一致）：
- `docs/project_control/EXECUTION_GUARDRAILS.md`

## 1. 保护：先补关键测试或增加断言/日志

在进行任何改动前，首先保证现有功能不会被破坏：

- 补充或确认现有的单元测试覆盖率
- 在关键逻辑处增加断言或日志，确保改动后可以清晰追踪行为

## 2. 计划：列出分步改动与回滚点

确保改动过程可控：

- 明确每个小步骤的目的与实现
- 标记关键的回滚点，以防止遇到问题时可以迅速恢复
- 为每个步骤定义期望行为，确保每个小改动都是原子化的

## 3. 执行：每步一个小 diff，保持可运行

进行实际的代码改动：

- 每次改动只做小规模的 diff，避免影响其他系统
- 保证每次改动后，系统依然保持可运行，最好能够通过现有测试验证
- 对改动的每一部分进行详细的代码注释，解释为何做此改动以及其带来的变化

## 4. 验证：每步跑测试/静态检查

确保每个小改动都符合预期：

- 每完成一个步骤后，运行现有的单元测试与静态检查（如 lint、格式化检查等）
- 在执行过程中，如果发现失败，停止并诊断问题
- 确保每一步的行为与期望一致，保持系统功能不变

## 5. 总结：说明收益、风险与后续建议

完成所有改动后，进行总结：

- **收益**：概述此次改动带来的主要好处，特别是在性能、可维护性或可扩展性上的改进
- **风险**：分析改动可能带来的潜在风险，特别是与行为变更、性能波动或回滚相关的风险
- **后续建议**：提出可能的后续工作，尤其是进一步优化或扩展的建议

---

# 6. 行为规范

此技能必须：

- 采取逐步、可验证的改动方式
- 确保每个改动都可回滚，且不会对现有功能产生负面影响
- 注重保持行为不变，确保系统功能在所有步骤完成后依旧一致
- 强调回归测试，确保每一步的功能验证完整

# 7. 与 dev-orchestrator 对齐规则（新增）

当重构任务属于阶段合约执行（尤其 `P0/P1`）时，额外遵循：

1. 测试先行门禁（MUST）
- 先新增/更新自动化测试脚本，再实施重构。
- 测试脚本必须可追溯到 `TC-ID`（测试名/注释/参数化 ID 任一）。

2. 状态同步门禁（MUST）
- 任务开始即写 `Doing`。
- 通过验证后先写 `test-evidence`，再写 `In review/done`。
- `P0/P1` 写 `In review/done` 时必须传 `--test-files`，且文件出现在当前 `git diff`。

3. 失败重试与离线补偿（MUST）
- Notion 写操作使用指数退避（1s/2s/4s，最多 3 次）。
- 连续失败后写入离线队列，网络恢复后回放。

4. 对账口径（MUST）
- 阶段末对账必须基于 `--milestone-id` 全量拉取后本地筛选 phase。
- 禁止仅依赖 `--task-prefix + --status` 判定完成度。

5. 命令执行安全（MUST）
- 禁止 `eval` 执行测试命令。
- 优先使用 `.venv/bin/python` 解析 JSON，不把 `jq` 作为必需依赖。

6. 结构化证据（SHOULD）
- 记录 `tmp/execution.log` 与 `tmp/errors.log`。
- 关键字段建议包含：`phase|task_id|action|status|duration`。
