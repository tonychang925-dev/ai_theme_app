一、计划评估
1️⃣ 合理性
严格遵守数据库隔离
新链算法仅通过 StockReadPort 读取数据，不直接操作数据库（禁止写操作）
所有中间数据写入 tmp/ 目录 JSON 文件，便于回放和对比
✅ 这一点符合“数据库操作由 database_service 数据 gateway 统一管理”的原则。
算法逻辑完整复刻
EnhancedMainlineJudgementService + MainlineJudgementService 逐行复刻，保持旧链评分和子类继承关系
6 个增强维度、K线占位方法保留（保持旧链逻辑一致性）
✅ 满足复刻旧链逻辑的要求，同时不会破坏数据库。
回放与对比机制
Layer A 回放 runner 对 4/7、4/15 样本做 JSON 输出对比
定义 exact/approx/mismatch 三类对比规则
✅ 可验证算法逻辑复刻准确性，并在不操作 DB 情况下完成验证。
2️⃣ 潜在风险或不足
数据源近似映射
新链从 SubjectContextDTO.metadata + StockBarDTO 构建 ThemeEventStats / ThemeMarketStats
旧链直接聚合 news_event/subject_stock_daily_snapshot 表
预期差异会导致评分字段小差异，尤其是连续事件链或 leader 统计
⚠️ 需要确保 tier 分类和关键样本 formal/alive 输出对齐。
Layer A/B/C/D 上游依赖
如果 Layer A 复刻完成，但 Layer B 或 C 输入覆盖域仍不完整，formal_rows 数量会受限，影响 downstream recap/top_candidates 输出
⚠️ 必须同时规划 Layer B 差距补齐策略。
JSON 输出管理
输出 tmp/ 目录文件用于回放和对比，如果后续多样本并行运行，需保证文件名和路径不冲突，并且缓存/读取逻辑统一。
协议兼容性
StockReadPort 的新增方法必须保持与 database_service gateway 对齐，否则后续真实运行可能无法读取所需数据。
二、优化建议
1️⃣ Layer A 算法复刻
继续使用 纯算法复刻 + JSON 输出，保持与旧链逻辑 1:1 对应。
对于增强维度/占位方法，保持默认值（0 或 TODO），确保不破坏算法链。
2️⃣ 数据读取与 gateway 对齐
所有数据访问仅通过 StockReadPort / DatabaseGatewayStockFacade
避免任何 asyncpg / SQL 直连
对缺失字段使用 保守默认值 并标注 _data_source: "approximated"
3️⃣ 回放与差异分析机制
JSON 输出与旧链数据库输出对比
建议增加自动差异统计模块，标注 exact/approx/mismatch，并生成可视化报告
对关键样本（如神剑/联德）确保 formal/alive 输出一致
4️⃣ Layer B/C 衔接规划
Layer A 复刻完成后，尽快制定 Layer B 补齐计划（KLine/退潮证据/板块聚合器）
Layer C UniverseBuilder 输入需对齐 Layer A/B 覆盖域，避免 formal_rows 数量不足
Recap/top_candidates 聚合仅在 Layer B 完整覆盖后才能最终验证
5️⃣ JSON 管理与自动化
为每次回放指定 trade_date + sample_name 生成唯一文件名
使用统一工具读取/解析 tmp/ 文件，便于批量对比和回归测试
三、结论

✅ 该计划总体合理：

完全复刻旧链算法逻辑
不直接操作数据库，严格依赖 data gateway
回放与对比机制可验证算法输出

⚠️ 需要注意的点：

数据源近似映射可能造成评分小差异
Layer B/C 输入覆盖不足可能影响 downstream
JSON 文件管理需规范化以支持大规模回放

建议：可先完成 Layer A 算法复刻和回放验证，在确认输出与旧链一致后，再分阶段补齐 Layer B、C，并保持数据库操作全通过 gateway，确保架构清晰、数据安全。
