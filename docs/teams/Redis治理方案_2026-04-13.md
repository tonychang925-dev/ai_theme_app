# Redis治理方案 (技术负责人)

## 方案概述
基于2026-04-13的Redis状态分析，制定Redis治理专项方案，解决内存泄漏风险和高pending消息问题。

## 一、当前问题分析

### 1.1 关键问题识别

#### P0级问题 (立即处理)
1. **高pending消息堆积**
   - Stream: `stream:events:normal`
   - 消费者组: `news_business_processors`
   - Pending消息: 1638条
   - 影响: 消息处理延迟，可能影响实时性

2. **非活跃消费者组内存泄漏风险**
   - 7个非活跃消费者组占用资源
   - 可能由测试代码动态创建未清理

#### P1级问题 (本周处理)
1. **消费者组管理不规范**
   - 测试组和正式组混合
   - 缺乏统一的命名规范
   - 缺少生命周期管理

2. **监控告警缺失**
   - 无pending消息监控
   - 无消费者组状态监控
   - 无内存使用告警

### 1.2 根本原因分析

1. **测试代码问题**: 测试时动态创建消费者组，测试结束后未清理
2. **消费者处理能力不足**: `news_business_processors`组处理速度跟不上消息产生速度
3. **缺乏治理机制**: 没有定期的清理和监控机制

## 四、技术方案细节

### 4.1 自动化清理脚本增强

#### 现有基础
```python
# database_service/streams/utils/consumer_group_manager.py
# 已实现功能:
# 1. ConsumerGroupManager类
# 2. cleanup_old_groups()方法
# 3. 测试组模式匹配
# 4. 保护组机制
```

#### 增强需求
1. **更精确的年龄判断**: 基于最后消息时间戳
2. **pending消息处理**: 清理前尝试处理剩余消息
3. **清理确认机制**: 重要组清理前需要确认
4. **清理报告**: 详细的清理报告和统计

#### 实现方案
```python
# 新增功能
1. 基于时间戳的年龄计算
2. pending消息转移或重试机制
3. 清理确认工作流
4. 定期任务调度集成
```

### 4.2 监控告警配置

#### 监控指标
1. **关键指标**:
   - `redis_memory_used_percentage` > 80% (警告), > 90% (严重)
   - `consumer_group_pending_messages` > 100 (警告), > 1000 (严重)
   - `inactive_consumer_groups` > 5 (警告)

2. **业务指标**:
   - `news_processing_delay` > 10秒 (警告)
   - `ai_processing_time` > 2秒 (警告)

#### 告警规则
1. **P0告警** (立即响应):
   - Redis内存 > 90%
   - Pending消息 > 1000
   - 消费者组全部宕机

2. **P1告警** (1小时内响应):
   - Redis内存 > 80%
   - Pending消息 > 100
   - 非活跃组 > 10

3. **P2告警** (当日处理):
   - 其他监控指标异常

### 4.3 性能优化方案

#### 瓶颈分析
1. **AI处理瓶颈**: 单条处理10-12秒
2. **消费者并发不足**: 当前66个消费者可能不足
3. **消息序列化开销**: JSON解析/序列化可能较慢

#### 优化策略
1. **短期优化**:
   - 增加消费者数量
   - 优化AI模型批处理
   - 使用更高效的消息格式

2. **中期优化**:
   - AI模型量化压缩
   - GPU加速推理
   - 结果缓存机制
