## 0. 结论

**可以作为开发总计划，建议修订到 v0.2 后再批准 P0-A。**

计划的骨架是对的：
- 依赖顺序：数据真实 → 可表达 → 分类 → 许可 → 资格 → 投影 → 切换 → 退役；

## 1. A 级：必须在批准前修改

### A-1　P0-C 会在不知不觉中打开交易许可

**问题**：P0C-02 的验收写的是“候选主线的周期证据要到达 MarketRegime / setup context”，P0-C 的出口又写着“no new trade permission created yet”。按现在的代码，这两条做不到同时成立。

**代码事实**：
- `MainlineEnvironmentEngine`（`market_regime/mainline_environment_engine.py:21–24`）只要看到某条周期复核的 `mainline_trade_alive=True`，并且状态是 `start / fermentation / acceleration / divergence / repair`，就把环境判为 `mainline_tradable`。
- 随后 `TradingPermissionEngine` 会给出 `allow_trade=True`，仓位 0.3 或 0.5。
- 它**不检查**这条复核来自候选主线还是已确认主线。

**后果**：候选主线的周期复核一旦按 P0C-02 送进 MarketRegime，在 P0-D（Owner 定义 EARLY）和 P0-E（许可层纠偏）**之前**，许可层就会从“无确认主线 → 不交易”变成“可交易、仓位 0.5”。而且候选主线大概率处在残差状态 `start`，它在许可层里本来就算“可交易”。

这正是 P0-C 出口禁止的事，但计划里没有任何机制防止它发生。

**修改建议**：P0C-01 和 P0C-02 增加一条硬约束：

```text
在 P0E-01 完成之前，所有现有消费者（MainlineEnvironment / TradingPermission /
OneToTwoRuleEngine / PDV2）只消费 identity_status = CONFIRMED 的对象；
CANDIDATE 对象只进入新增的、尚无消费者的字段或诊断区。
```

验收增加一条**回归断言**：同一份回放数据，P0-C 前后 `market_regime_review.allow_trade`、`position_limit`、1进2 的各项决策**逐日完全一致**。

另外，1进2 规则引擎 `:38` 的否决条件是“既非已确认主线也非强热点”。候选主线进入事实上下文后，也不能被顺手映射成 `is_strong_hotspot`。

### A-2　弱转强的“缺失 → 通过”被不必要地压在 OP-06 后面

**问题**：依赖链是 P0G-01 ← P0E ← P0D-02 ← **Owner 关口 OP-06** ← EARLY 回放研究。弱转强候选里三处在线的“缺失 → 通过”，都被放在 P0G-03，要排在这条链后面：

- W-07：周线数据缺失 → `passed=True`；
- W-09：前一状态未知 → 软通过，默认开启；
- W-11：强势等级缺失 → `"B"`。

**为什么不该这样排**：
- 这三项和 P0B 的问题性质完全相同，都是“数据真实性 / 缺失即关闭”，**与 EARLY 毫无关系**。
- 弱转强本身也不依赖 EARLY：它要求的是已确认主线 + 分歧 → 修复。
- OP-06 要等回放研究和 Owner 决定，可能拖很久。这期间，这三个缺口会在盘前简报里每天产出候选。

**修改建议**：
1. 把 W-07、W-09、W-11 的“缺失即关闭”拆成 **P0B-05**，与 P0B-04（统一预警）同批进行。只改缺失处理，不改评分和资格语义。
2. 把 P0E-01 拆开：
   - **P0E-01a**：与 EARLY 无关的许可纠偏，包括普通 RISK_OFF 不自动否决弱转强、题材 FADE 否决弱转强、allow 与 prohibit 不冲突。它依赖 P0B，**不依赖** OP-06。
   - **P0E-01b**：候选主线 + EARLY 的试错许可。它依赖 P0D-02。
3. P0G 改为依赖 P0E-01a。这样弱转强这条线不会被 OP-06 卡住。

## 2. B 级：不改的话验收没法落地

### B-1　P0A-01 的守卫测试必须是“棘轮”，否则第一天就全红

- **问题**：验收要求“已知的 P0 违规全部能检测出来”。如果检测到就失败，那么在现有代码上测试会立刻失败。仅 Domain 层就有 9 个文件、Application 层有 20 多个文件存在违规，CI 从第一天起就是红的，团队只能关掉它。
- **修改建议**：写明采用**基线 + 棘轮**：
  - 现有违规登记进一个白名单（基线），每一项带上清单编号，例如 P0A2 §2.2 的 A / B / C 类；
  - 测试只在出现**新的**违规时失败；
  - 修复一项就从白名单删掉一项，白名单只能缩短、不能变长。
- **可复用的先例**：仓库里已经有 `stock_processing_service/tests/unit/test_canonical_metrics_migration_guard.py`，它基于 `ast` 做静态检查。P0A-01 应该沿用这个风格，不要另起一套机制。

### B-2　P0A-02 的“新增规则没有登记就失败”无法机械判定

- **问题**：什么是一条“可执行规则”，静态分析判断不出来：一个 `>= 0.08` 可能是规则，也可能是格式化代码。这条验收没有办法自动化。
- **修改建议**：拆成三件可以验证的事：
  1. **登记表**：清单 1 的 86 条转成机器可读文件，每条有 rule_id、路径、符号、当前值、分类。
  2. **钉住测试**：对登记表里的每一条，测试会读取代码中的当前值；值或位置一旦变化，测试就失败，提示必须同步修改登记表和分类。
  3. **PR 清单**：新增的阈值靠 PR 模板中的必填项和人工审查兜底，不承诺自动检测。

### B-3　P0A-03 和 P0B-01 / 02 会改同一个文件两次

- **问题**：`market_regime_fact_context_builder.py` 在 P0A-03 中要做“边界修复”，而且要求和现有查询**语义完全一致**；随后 P0B-01、P0B-02 又要改掉它的默认快照和 akshare 兜底。
- **后果**：P0A-03 必须小心保住“默认快照”和“未来函数”这两个随后就要删掉的行为，才能通过“一致性”验收。同一个文件两轮修改、两轮回放，没有必要。
- **修改建议**：P0A-03 的范围去掉这个文件，把它的边界修复并入 P0B-01 / 02。这三项合起来，正好是“这个文件的数据怎么来”这一个问题。P0A-03 只保留复盘任务的 Port 穿透和 `mainline_logic_chain_builder`。

### B-4　P0D-01 的回放研究需要 Tony 提供标注，计划里没有这个关口

- **问题**：研究要用到“真正的 EARLY → 后来成为主线”的正例和“假启动 / 一日游”的反例。哪个题材在哪一天算真正的初期，本身就是**策略判断**。按 v0.6.4，这只能由 Tony 定，不能由实施方从事后结果里倒推。
- **修改建议**：在 P0D-01 前面增加 **P0D-00：Owner 标注**。
  - 实施方先提出候选样本（日期 + 题材 + 当时可见的证据），由 Tony 逐条标注“是 / 否 / 不确定”。
  - 标注完成后冻结，作为验证集。
  - 昊哥那批“待裁定的标注表”（v2 验证报告 §3）也可以在同一次处理。

## 4. 一个不需要写代码、Tony 现在就能做的决定

统一预警循环（P0B-04 的对象）**现在每分钟都在推送**，而且会拿旧候选发今天的预警，资金数据缺失时也能给出“高置信”。

它由环境变量控制：`api_app.py:269`，`SPS_ENABLE_W2S_ALERT_LOOP`，默认是 `"true"`。在 P0B-04 合并之前，Tony 可以选择：

- **关掉**：设为 `false` 并重启 API。没有预警，但也不会有错误的预警。
- **保持开启**：已知这两个缺陷存在，看到“高置信”预警时自行核对。

这是运维层面的决定，不是代码修改，所以不在计划的授权范围里，但值得在批准计划时一起定下来。
