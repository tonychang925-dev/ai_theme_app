# 前端架构优化方案 - 实时通信与三栏布局

## 概述

基于"个人投资助理项目-前端技术设计（第四阶段）"和"个人投资助理项目-前端技术设计（第四阶段前置版）"设计文档的分析，本方案旨在解决当前实现与设计规范之间的关键差距。

**优化重点：**
1. 统一实时通信架构（解决SSE与WebSocket冲突）
2. 实现三栏"投研作战台"布局
3. 完善功能模块（主题雷达、市场验证）
4. 对齐每日复盘数据结构

## 一、当前问题诊断

### 1.1 实时通信架构冲突
| 设计文档要求 | 当前实现 | 冲突影响 |
|-------------|---------|---------|
| SSE (Server-Sent Events) + `/api/intel/feed` 轮询兜底 | WebSocket (`/ws/realtime`) + SSE (`/api/intel/stream`) 双轨制 | 架构决策不一致，增加维护复杂性 |

### 1.2 布局架构缺失
| 设计文档要求 | 当前实现 | 功能差距 |
|-------------|---------|---------|
| 三栏式"投研作战台"布局 | 单栏式IntelPage | 缺失主题雷达、市场验证模块 |
| - 左栏：主题雷达（主题选择与筛选） | - 仅中间栏：AI事件流 | - 主题筛选功能缺失 |
| - 中栏：AI事件流（核心情报展示） | - 无左右辅助面板 | - 市场验证功能缺失 |
| - 右栏：市场验证（技术分析与验证） | | - 信息视图不完整 |

### 1.3 功能模块不完整
| 模块 | 设计功能 | 当前状态 |
|-----|---------|---------|
| **主题雷达** | 主题热度可视化、主题筛选、快速导航 | 完全缺失 |
| **市场验证** | 技术指标验证、资金流向分析、K线模式识别 | 完全缺失 |
| **每日复盘** | 结构化数据模型（MarketSummary, ThemeReview等） | 存在但数据结构不完全对齐 |

### 1.4 技术债务
- 前端状态管理缺乏统一方案
- 组件间通信机制不够清晰
- 错误处理和重试机制需要加强

## 二、优化方案

### 2.1 实时通信架构统一（优先级1）

#### 目标
确立清晰的实时数据流层次结构，明确SSE为主方案，WebSocket为可选高级功能。

#### 具体措施
1. **明确SSE为主方案**
   - 文档明确：`/api/intel/stream` (EventSource/SSE) 为主要实时数据通道
   - 保持现有`openIntelStream()` API不变
   - 强化SSE连接管理和错误恢复机制

2. **WebSocket降级为可选功能**
   - 保留WebSocket (`/ws/realtime`) 作为高级/双向通信选项
   - 更新文档说明适用场景：需要客户端->服务器命令的场景
   - 标记为非必需依赖，不影响核心功能
   - 更新API端点注释和返回数据结构

3. **轮询兜底机制优化**
   - 优化现有30秒轮询间隔策略
   - 增加智能退避机制（网络异常时延长间隔）
   - 统一错误处理和状态提示

#### 架构调整
```yaml
实时通信层次结构：
1. 主要通道：SSE (/api/intel/stream)
   - 类型：单向服务器->客户端推送
   - 用途：AI事件流实时更新
   - 客户端：EventSource API

2. 轮询兜底：REST API (/api/intel/feed)
   - 类型：客户端主动轮询
   - 用途：SSE不可用时的降级方案
   - 间隔：智能调整（默认30秒）

3. 可选高级：WebSocket (/ws/realtime)
   - 类型：双向通信
   - 用途：需要客户端命令的场景
   - 状态：可选，非必需
```

### 2.2 三栏布局实现（优先级2）

#### 目标
实现设计文档中的三栏"投研作战台"布局，提供完整的投资决策支持界面。

#### 布局结构
```
+-----------------------------------------+
| 主题雷达 (左栏) | AI事件流 (中栏) | 市场验证 (右栏) |
| Width: 280px    | Width: 自适应     | Width: 320px    |
+-----------------------------------------+
```

#### 具体措施
1. **创建三栏布局组件** (`ThreeColumnLayout`)
   - 响应式设计：桌面三栏，移动端堆叠
   - 可调整列宽：支持用户偏好设置
   - 统一状态管理：跨栏数据同步机制

2. **开发主题雷达模块** (`ThemeRadarPanel`)
   - 热度可视化：雷达图/热力图展示主题热度
   - 筛选功能：按热度、阶段、关联股票数筛选
   - 快速导航：点击主题直接跳转主题详情页
   - 实时更新：与中栏事件流联动

3. **开发市场验证模块** (`MarketValidationPanel`)
   - 技术指标面板：MACD, RSI, 成交量等
   - 资金流向分析：主力资金、散户资金流向
   - K线模式识别：常见技术形态标注
   - 关联展示：当前选中事件的相关股票验证

4. **重构IntelPage为中间栏** (`IntelStreamPanel`)
   - 提取现有IntelPage核心逻辑
   - 优化为纯展示组件
   - 增加与左右栏的联动API

### 2.3 每日复盘模块优化（优先级3）

#### 目标
对齐设计文档中的数据结构，改善用户体验。

#### 具体措施
1. **数据结构对齐**

2. **UI/UX优化**
   - 按照设计文档优化信息架构
   - 改善可读性和交互性
   - 增加数据可视化元素

### 2.4 代码质量与架构优化（优先级4）

#### 具体措施
1. **API层统一**
   - 统一错误处理模式

   - 优化TypeScript类型定义

2. **状态管理评估**
   - 评估是否需要引入状态管理库（Zustand/Redux）

## 四、技术决策点

### 4.1 状态管理方案
| 选项 | 优点 | 缺点 | 推荐度 |
|------|------|------|--------|
| 保持现有React状态 + Context | 简单，无额外依赖 | 跨组件状态共享复杂 | 评估后决定 |
| 引入Zustand | 轻量级，React友好 | 增加学习成本 | ★★★★☆ |
| 引入Redux Toolkit | 成熟，生态丰富 | 相对复杂 | ★★★☆☆ |

**建议**：评估组件间状态共享需求后决定。若三栏联动复杂，推荐Zustand。

### 4.2 图表库选择
| 库 | 优点 | 缺点 | 适用场景 |
|----|------|------|----------|
| Recharts | React原生，简单易用 | 功能相对基础 | 雷达图、热力图 |
| Chart.js | 功能丰富，文档完善 | React集成需要适配器 | K线图、资金流向图 |
| ECharts | 功能最强大，可视化效果好 | 体积较大，文档中文为主 | 复杂可视化需求 |

**建议**：Recharts + 定制组件，满足80%需求。

### 4.3 响应式断点设计
```css
/* 桌面端：三栏布局 */
@media (min-width: 1200px) {
  .three-column-layout { grid-template-columns: 280px 1fr 320px; }
}

/* 平板端：两栏布局 */
@media (min-width: 768px) and (max-width: 1199px) {
  .three-column-layout { grid-template-columns: 280px 1fr; }
}

/* 移动端：单栏堆叠 */
@media (max-width: 767px) {
  .three-column-layout { grid-template-columns: 1fr; }
}
```

## 五、风险与缓解措施

### 5.1 性能风险
| 风险 | 影响 | 缓解措施 |
|------|------|----------|
| 三栏同时更新影响性能 | 页面卡顿，响应延迟 | 虚拟滚动、请求合并、懒加载 |
| 实时数据流过大 | 内存占用高，CPU使用率高 | 分页加载、增量更新、数据压缩 |

### 5.2 兼容性风险
| 风险 | 影响 | 缓解措施 |
|------|------|----------|
| 旧版本浏览器SSE支持 | 实时功能不可用 | 完备的轮询兜底机制 |
| 移动端性能限制 | 复杂布局渲染慢 | 移动端简化视图、按需加载 |

### 5.3 开发复杂度风险
| 风险 | 影响 | 缓解措施 |
|------|------|----------|
| 三栏联动状态管理复杂 | 开发周期延长，bug增多 | 清晰的接口定义、逐步实现 |
| 数据一致性维护困难 | 数据不同步，用户体验差 | 统一数据更新时间戳、乐观更新 |

### 5.4 集成风险
| 风险 | 影响 | 缓解措施 |
|------|------|----------|
| 新模块与现有系统集成问题 | 功能冲突，回归问题 | 充分测试、渐进式迁移 |
| 后端API变更影响 | 前端功能失效 | API版本管理、向后兼容 |

## 九、架构说明

### 9.1 实时通信架构（阶段1完成）

#### 主要变更
1. **统一实时通信层次结构**：
   - 主要通道：SSE (`/api/intel/stream`) - 单向服务器->客户端推送
   - 轮询兜底：REST API (`/api/intel/feed`) - 智能退避机制
   - 可选高级：WebSocket (`/ws/realtime`) - 标记为可选功能，用于需要双向通信的场景

2. **SSE连接管理优化**：
   - 创建增强的SSEManager类 (`frontend/src/lib/realtime/sseManager.ts`)
   - 功能：自动重试、智能退避、心跳监控、连接状态管理
   - 配置选项：最大重试次数、重试延迟、心跳超时、连接超时
   - 事件处理器：`onIntelItem`, `onHeartbeat`, `onStateChange`, `onError`, `onClose`

3. **IntelPage组件集成**：
   - 替换原有EventSource为SSEManager
   - 添加连接状态监控和显示
   - 实现智能轮询兜底机制（错误时指数退避）

4. **API层更新**：
   - 保留向后兼容的`openIntelStream()`函数
   - 新增`createIntelStreamManager()`函数（推荐使用）
   - 导出SSEManager相关类型

#### 技术实现要点
- **SSEManager选项**：默认最大重试3次，初始延迟1000ms，退避因子2.0
- **心跳机制**：45秒超时，服务器每15秒发送心跳
- **状态管理**：6种连接状态（disconnected, connecting, connected, retrying, error, closed）
- **轮询退避**：30秒基础间隔，错误时指数退避，最大5分钟间隔

### 9.2 使用指南

#### 新组件开发
```typescript
import { createIntelStreamManager, SSEEventHandlers } from '../lib/api';

const manager = createIntelStreamManager(
  { date: '2026-04-10', type: 'all', session: 'all' },
  {
    onIntelItem: (event) => { /* 处理新情报项 */ },
    onStateChange: (state) => { /* 更新连接状态UI */ },
  },
  { maxRetries: 5, heartbeatTimeout: 60000 }
);

manager.connect();
// 组件卸载时调用 manager.disconnect();
```

#### 现有组件迁移
- 逐步替换`openIntelStream()`为`createIntelStreamManager()`
- 利用`onStateChange`回调增强连接状态显示
- 根据业务需求调整重试策略
