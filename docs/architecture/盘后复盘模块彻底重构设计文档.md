<span id="0-文档目的"></span>
## 0. 文档目的

本设计文档用于彻底修正当前"日采集控制台"和"当日复盘"之间职责混乱的问题，将系统拆分为两个清晰模块：

```text
模块一：采集模块
职责：每日基础数据采集
入口：日采集控制台

模块二：复盘模块
职责：每日动态复盘数据生成 + 复盘报告展示
入口：当日复盘页面
```

本次重构的核心目标不是继续修补某个空字段，而是恢复清晰的工程边界：

```text
采集模块只采集原材料
复盘模块负责加工每日动态结果
展示模块只展示复盘快照
```

<span id="1-当前问题复盘"></span>
## 1. 当前问题复盘

### 1.1 当前实际问题

1. 日采集控制台显示"完整执行"，但复盘报告大量字段为空
2. `subject_stock_daily_snapshot` 有 26K 数据，但复盘核心表为 0
3. 复盘页面缺失：主线与支线、主线资金流入前10、强势股分层、龙虎榜
4. `strong_stock_watch` 控制台任务是假成功
5. `recap_snapshot` 在真源表未准备好时仍写入空快照
6. 前端新增"主线与支线（结构化）"偏离 5/22 已验收样式

### 1.2 根因总结

```text
日采集控制台 ≠ 复盘数据完成
复盘快照生成 ≠ 真源表已就绪
控制台全绿 ≠ 复盘报告可展示
```

<span id="2-总体架构重构目标"></span>
## 2. 总体架构重构目标

### 2.1 新架构总览

```text
外部数据源 (JYHF / Tushare / 龙虎榜 / 竞价 / 原始异动)
        ↓
【模块一】采集模块（日采集控制台）
        ↓
基础数据表 / 原始数据表
        ↓
【模块二】复盘模块（当日复盘页面）
    阶段一：每日动态复盘数据生成
        ↓
    复盘真源表 / 派生结果表
        ↓
    阶段二：复盘报告展示
        ↓
post_market_recap_snapshot / DailyReview / 前端 5/22 样式展示
```

### 2.2 两个模块的边界

| 模块 | 页面入口 | 职责 | 禁止 |
| --- | --- | --- | --- |
| 采集模块 | 日采集控制台 | 采集每日基础数据、原始数据、基础快照 | 不生成复盘报告、不负责题材周期结论、不负责最终复盘展示 |
| 复盘模块 | 当日复盘页面 | 生成每日动态复盘数据、生成复盘快照、展示复盘报告 | 不重新采集外部基础数据、不修改采集控制台逻辑 |

### 2.3 核心原则

1. 采集模块只做"原材料入库"
2. 复盘模块负责"基于原材料计算每日动态结果"
3. 复盘模块内部必须拆成两个阶段：阶段一（动态数据生成）、阶段二（报告展示）
4. read-only 只能用于已完成动态数据生成之后的重新封装/渲染
5. 不允许在真源数据不完整时写入成功快照
6. 前端展示样式必须保持 5/22 已验收版本

<span id="3-模块一采集模块设计"></span>
## 3. 模块一：采集模块设计

### 3.1 模块定位

采集模块沿用当前"日采集控制台"功能。职责：**把每日基础数据采集进数据库。**

采集模块不负责：题材周期判断、强势股分层计算、资金行为增强、复盘报告生成、DailyReview生成、前端复盘展示。

### 3.2 日采集控制台保留任务

| 任务 | 目标产物 | 说明 |
|------|---------|------|
| JYHF / 股票快照 | `subject_stock_daily_snapshot` | 题材列表、节点、详情、股票日快照 |
| Tushare 日K线 / 竞价 | `stock_daily_bar`, `auction_snapshot` | 基础行情数据 |
| 龙虎榜原始数据 | raw dragon tiger rows | 龙虎榜原始采集 |
| 异动股票基础数据 | abnormal raw inputs | 异动候选输入 |
| 龙头候选 LLM 裁决 | `leader_llm_queue/candidate` | LLM裁决输入与结果 |

### 3.3 采集模块不得出现的行为

1. 生成 `post_market_recap_snapshot`
2. 显示"复盘报告已生成"
3. 假成功（status=success 但目标表为空）
4. 把复盘真源计算藏在采集任务里
5. 直接触发 RecapPage 的复盘展示刷新

<span id="5-复盘模块阶段一每日动态复盘数据生成"></span>
## 5. 复盘模块阶段一：每日动态复盘数据生成

### 5.1 执行流程

```text
Step 0：基础采集数据 readiness 检查
Step 1：题材周期真源生成 (theme_cycle_truth)
Step 2：龙虎榜对象化 (dragon_tiger_object_build)
Step 3：资金行为增强 (money_flow_enhanced_build)
Step 4：强势股跟踪池生成 (strong_stock_watch_build)
Step 5：复盘真源 readiness 检查
```

### 5.2 目标产物与验收

| Step | 目标表 | 验收 SQL | 要求 |
|------|--------|---------|------|
| 1 | `theme_cycle_judgement_v2` | `select count(*) where trade_date=:d` | rows > 0 |
| 2 | `dragon_tiger_object` | `select count(*) where trade_date=:d` | rows > 0 或 skipped_no_data |
| 3 | `money_flow_enhanced` | `select count(*) where trade_date=:d` | rows > 0 |
| 4 | `strong_stock_watch_history` | `select count(*) where trade_date=:d` | rows > 0 |
| 5 | readiness check | 5表全部检查 | ready / failed_precondition |

<span id="6-复盘模块阶段二复盘报告展示"></span>
## 6. 复盘模块阶段二：复盘报告展示

阶段二才是 read-only。负责：读取复盘真源表 → 封装 DailyReview → 写入快照 → 前端 5/22 样式展示。

阶段二不负责：重新采集外部数据、重新计算题材周期/强势股分层/资金行为增强。

### 6.1 DailyReview 结构

<span id="12-状态机设计"></span>
## 12. 状态机设计

```text
NOT_COLLECTED → BASE_READY → DERIVING → DERIVED_READY → RECAP_GENERATING → RECAP_READY
                                         ↘ FAILED_PRECONDITION
                                         ↘ FAILED
```

新增 `post_market_job_status` 表：

```sql
create table if not exists post_market_job_status (
    id bigserial primary key,
    trade_date date not null,
    job_key text not null,
    status text not null,
    started_at timestamptz,
    finished_at timestamptz,
    error_code text,
    error_message text,
    diagnostics jsonb default '{}'::jsonb,
    created_at timestamptz default now(),
    updated_at timestamptz default now(),
    unique (trade_date, job_key)
);
```

<span id="13-错误处理规则"></span>
## 13. 错误处理规则

1. **不允许假成功**：目标表 rows=0 时，状态必须是 `skipped_no_data` / `failed_no_rows` / `failed_precondition`
2. **不允许覆盖完整快照**：readiness 不通过时，不允许写 `post_market_recap_snapshot`
3. **partial 明确化**：部分生成必须在 diagnostics 中记录 `missing_sections`

<span id="21-dailyreview-v2-页面级数据契约"></span>
## 21. DailyReview V2 页面级数据契约

### 21.0 设计结论

前端设计原则已经明确：前端是认知放大器，不负责理解和制造决策；组件结构要与后端数据模型一一对应。盘后复盘模块不是新闻汇总，而是对当天市场逻辑验证、失效和沉淀的结构化总结。

因此，DailyReview V2 必须覆盖 `/recap?date=YYYY-MM-DD&report_type=post_market` 的完整主体页面，而不是只覆盖 `theme_reviews`。当前 P0 已经回到 `sections_first`，这是止血状态；DailyReview V2 完整实现并通过契约测试后，才能切换为 `daily_review_v2_first`。

未来主体展示链路从：

```text
payload.sections
  -> parseThemeSummary()
  -> parseStrongStockBody()
  -> parseAbnormalSignalRow()
  -> parseDragonTigerRow()
```

迁移为：

```text
dailyReviewV2
  -> market_summary
  -> theme_reviews
  -> theme_capital_reviews
  -> strong_stock_reviews
  -> watchlist_reviews
  -> stock_capital_reviews
  -> abnormal_reviews
  -> money_flow_reviews
  -> dragon_tiger_reviews
```

### 21.1 页面级 DTO：PostMarketDailyReviewV2

V2 新增独立接口，不继续扩展 V1 `DailyReviewView`，避免 V1 diagnostics-only 与 V2 主体 ViewModel 混淆。

```ts
export interface PostMarketDailyReviewV2 {
  schema_version: "daily_review_v2";
  trade_date: string;
  report_type: "post_market";
  snapshot_version: string;
  generated_at: string;

  data_mode: "daily_review_v2_first";
  source: {
    snapshot_id?: string;
    recap_snapshot_version?: string;
    derived_data_status: "ready" | "failed_precondition" | "partial";
    recap_generate_status: "success" | "skipped_idempotent" | "failed";
  };

  market_summary: MarketSummaryReview;

  theme_reviews: ThemeReviewV2[];
  theme_capital_reviews: ThemeCapitalReview[];
  strong_stock_reviews: StrongStockReviewV2[];
  watchlist_reviews: WatchlistReview[];
  stock_capital_reviews: StockCapitalReview[];
  abnormal_reviews: AbnormalStockReview[];
  money_flow_reviews: MoneyFlowReview[];
  dragon_tiger_reviews: DragonTigerReview[];

  trading_principle: TradingPrincipleReview;
  diagnostics: DailyReviewDiagnostics;
}
```

设计硬约束：

1. 顶层必须有 `schema_version = "daily_review_v2"`。
2. 每个页面模块都有独立数组。
3. 每个数组直接对应一个前端模块。
4. 每个模块都能表达有数据、无数据、部分数据、失败原因。
5. `sections` 只作为 `legacy_fallback`，不是 V2 主体字段。

`capital_reviews` 不再承担龙虎榜主体展示职责，因为命名过泛。短期兼容时可以由后端执行 `dragon_tiger_reviews = capital_reviews.map(...)`，但前端禁止直接用 `capital_reviews` 渲染龙虎榜。

### 21.11 diagnostics 设计

DailyReview V2 必须解决“页面没数据时不知道哪个环节断了”的长期问题。

```ts
export interface DailyReviewDiagnostics {
  module_coverage: {
    market_summary: ModuleCoverage;
    theme_reviews: ModuleCoverage;
    theme_capital_reviews: ModuleCoverage;
    strong_stock_reviews: ModuleCoverage;
    watchlist_reviews: ModuleCoverage;
    stock_capital_reviews: ModuleCoverage;
    abnormal_reviews: ModuleCoverage;
    money_flow_reviews: ModuleCoverage;
    dragon_tiger_reviews: ModuleCoverage;
  };

  source_tables: Record<string, number>;

  warnings: string[];
  errors: string[];

  legacy_sections_available: boolean;
  legacy_section_counts: Record<string, number>;
}

export interface ModuleCoverage {
  status: "ready" | "empty" | "partial" | "failed";
  row_count: number;
  required: boolean;
  source: "structured" | "legacy_sections" | "none";
  missing_fields: string[];
  upstream_tables: Record<string, number>;
  message?: string;
}
```

前端空态优先读取 `diagnostics.module_coverage.<module>.message`，不得只显示泛泛的“暂无数据”。

### 23.8 关键路径与并行策略

关键路径：

```text
V2-P0 契约冻结
  -> V2-P1 Builder + API
  -> V2-P2 前端灰度入口
  -> V2-P3 模块灰度迁移
  -> V2-P4 契约测试
  -> V2-P5 默认切换
```

可并行任务：

1. V2-P1-T04~T12 各模块 builder 可以在 V2-P1-T03 后并行。
2. V2-P2-T01 类型定义可与 V2-P1 builder 开发并行，但必须以文档 schema 为准。
3. V2-P4-T01 后端 API contract 与 V2-P4-T02 前端静态 contract 可以并行。

阻塞节点：

1. V2-P1-T03 context 标准化失败会阻塞所有模块 builder。
2. V2-P1-T14 GET API 不稳定会阻塞前端灰度。
3. V2-P4 任一契约测试失败，不允许 V2-P5 默认切换。
