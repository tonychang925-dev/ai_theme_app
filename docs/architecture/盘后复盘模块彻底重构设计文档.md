## 0. 文档目的

本设计文档用于彻底修正当前"日采集控制台"和"当日复盘"之间职责混乱的问题，将系统拆分为两个清晰模块：

```text
模块一：采集模块
职责：每日基础数据采集
入口：日采集控制台

模块二：复盘模块
职责：每日动态复盘数据生成 + 复盘报告展示
入口：当日复盘页面
```

本次重构的核心目标不是继续修补某个空字段，而是恢复清晰的工程边界：

```text
采集模块只采集原材料
复盘模块负责加工每日动态结果
展示模块只展示复盘快照
```

# 1. 当前问题复盘

## 1.1 当前实际问题

当前系统出现的问题包括：

1. 日采集控制台显示"完整执行"，但复盘报告大量字段为空。
2. `subject_stock_daily_snapshot` 有 26K 数据，但以下复盘核心表为 0：
   - `theme_cycle_judgement_v2`
   - `dragon_tiger_object`
   - `money_flow_enhanced`
   - `strong_stock_watch_pool`
   - `strong_stock_watch_history`
3. 复盘页面缺失：
   - "主线与支线"中的题材K线 / 事件分 / 市场分
   - "主线资金流入前10"
   - "强势股分层"中的资金量能 / 结构位置 / 抗跌承接
   - "龙虎榜"
4. `strong_stock_watch` 控制台任务当前是假成功：显示成功，但并未实际写入 `strong_stock_watch_pool/history`。
5. `recap_snapshot` 曾被错误收缩为 read-only 生成，导致在复盘真源表未准备好时仍然写入空快照。
6. 前端曾新增"主线与支线（结构化）"展示样式，偏离 5/22 已验收页面样式。

## 1.2 根因总结

当前根因不是单个接口或字段问题，而是职责边界混乱：

```text
日采集控制台
被误认为应该完成所有复盘数据准备；

复盘快照生成
一度被误收缩为简单 read-only；

复盘页面
一度新增非 5/22 样式的展示结构。
```

正确认知应为：

```text
日采集控制台 = 原始数据采集
当日复盘页面 = 复盘动态数据生成 + 复盘报告展示
```

# 2. 总体架构重构目标

## 2.1 新架构总览

```text
外部数据源
JYHF / Tushare / 龙虎榜 / 竞价 / 原始异动
        ↓
【模块一】采集模块（日采集控制台）
        ↓
基础数据表 / 原始数据表
        ↓
【模块二】复盘模块（当日复盘页面）
    阶段一：每日动态复盘数据生成
        ↓
    复盘真源表 / 派生结果表
        ↓
    阶段二：复盘报告展示
        ↓
post_market_recap_snapshot / DailyReview / 前端 5/22 样式展示
```

## 2.2 两个模块的边界

| 模块 | 页面入口 | 职责 | 不允许做什么 |
| --- | --- | --- | --- |
| 采集模块 | 日采集控制台 | 采集每日基础数据、原始数据、基础快照 | 不生成复盘报告、不负责题材周期结论、不负责最终复盘展示 |
| 复盘模块 | 当日复盘页面 | 生成每日动态复盘数据、生成复盘快照、展示复盘报告 | 不重新采集外部基础数据、不修改采集控制台逻辑 |

## 2.3 核心原则

1. 采集模块只做"原材料入库"。
2. 复盘模块负责"基于原材料计算每日动态结果"。
3. 复盘模块内部必须拆成两个阶段：
   - 阶段一：每日动态复盘数据生成
   - 阶段二：复盘报告展示
4. read-only 只能用于"已完成动态数据生成之后，仅重新封装/渲染报告"。
5. 不允许在真源数据不完整时写入成功快照。
6. 前端展示样式必须保持 5/22 已验收版本，不允许重新设计页面。

# 3. 模块一：采集模块设计

## 3.1 模块定位

采集模块沿用当前"日采集控制台"功能。

它的职责是：

```text
把每日基础数据采集进数据库。
```

采集模块不负责：

```text
题材周期判断
强势股分层计算
资金行为增强
复盘报告生成
DailyReview 生成
前端复盘展示
```

## 3.2 日采集控制台保留任务

日采集控制台保留以下基础采集任务：

### 3.2.1 JYHF / 股票快照采集

目标产物：

```text
subject_stock_daily_snapshot
subject_node / subject_detail / subject_stock_map 等基础题材与股票数据
```

职责：

```text
采集题材列表、题材详情、股票详情、题材股票池与日快照。
```

验收：

```sql
select count(*)
from subject_stock_daily_snapshot
where trade_date = :trade_date;
```

要求：

```text
rows > 0
```

### 3.2.2 Tushare 日K线 / 竞价采集

目标产物：

```text
stock_daily_bar
auction_watch_universe
auction_snapshot
auction_signal
```

职责：

```text
采集股票日K线、竞价快照、竞价信号。
```

注意：

```text
这些是基础行情数据，不等于复盘中的强势股分层结论。
```

### 3.2.3 龙虎榜原始数据采集

目标产物：

```text
raw dragon tiger source rows
或 Tushare 龙虎榜原始数据表
```

职责：

```text
采集当天龙虎榜原始数据。
```

注意：

```text
dragon_tiger_object 不属于采集模块的最终职责。
它属于复盘模块阶段一中的"龙虎榜对象化"。
```

### 3.2.4 异动股票基础数据采集

目标产物：

```text
stock abnormal raw inputs
基础异动候选 / 行情异动输入
```

职责：

```text
采集或准备异动股票计算所需基础输入。
```

### 3.2.5 龙头候选 LLM 裁决输入 / 结果采集

目标产物：

```text
leader_llm_queue
leader_llm_judgement
leader_llm_candidate
```

职责：

```text
采集或生成龙头候选裁决相关输入与结果。
```

注意：

```text
leader_llm_candidate 不是复盘强势股分层的完整结果。
强势股分层仍需在复盘模块阶段一中基于多源数据计算。
```

## 3.3 采集模块状态输出

日采集控制台只展示基础采集状态，不再展示"复盘报告生成成功"。

建议新增采集状态表：

```json
{
  "trade_date": "2026-05-26",
  "collection_status": {
    "subject_stock_daily_snapshot": {
      "rows": 26316,
      "status": "ready"
    },
    "stock_daily_bar": {
      "rows": 5200,
      "status": "ready"
    },
    "auction_snapshot": {
      "rows": 5200,
      "status": "ready"
    },
    "dragon_tiger_raw": {
      "rows": 100,
      "status": "ready"
    },
    "leader_llm_candidate": {
      "rows": 80,
      "status": "ready"
    }
  }
}
```

## 3.4 采集模块不得出现的行为

采集模块不允许：

```text
1. 生成 post_market_recap_snapshot
2. 显示"复盘报告已生成"
3. 假成功，例如 strong_stock_watch 不执行但返回 success
4. 把复盘真源计算藏在采集任务里
5. 直接触发 RecapPage 的复盘展示刷新
```

# 4. 模块二：复盘模块设计

## 4.1 模块定位

复盘模块入口迁移到"当日复盘"页面。

复盘模块分为两大阶段：

```text
阶段一：每日动态复盘数据生成
阶段二：复盘报告展示
```

复盘模块的职责是：

```text
基于日采集控制台已经采集完成的基础数据，
计算当天的题材周期、资金行为、强势股分层、龙虎榜对象，
然后封装为 DailyReview 和 post_market_recap_snapshot。
```

---

# 5. 复盘模块阶段一：每日动态复盘数据生成

## 5.1 阶段一定位

阶段一不是 read-only。

阶段一是：

```text
Daily Derivation / 每日动态结果计算
```

它负责把采集来的原始数据加工为复盘报告真正使用的真源表。

## 5.2 阶段一执行流程

```text
Step 0：基础采集数据 readiness 检查
Step 1：题材周期真源生成
Step 2：龙虎榜对象化
Step 3：资金行为增强
Step 4：强势股跟踪池生成
Step 5：复盘真源 readiness 检查
```

## 5.3 Step 0：基础采集数据 readiness 检查

检查日采集控制台是否已经完成基础数据准备。

检查项：

| 检查项 | 表 | 要求 |
| --- | --- | --- |
| 股票快照 | `subject_stock_daily_snapshot` | rows > 0 |
| 日K线 | `stock_daily_bar` 或实际日K线表 | rows > 0 |
| 龙虎榜原始数据 | raw 龙虎榜表 | rows > 0 或 skipped_no_data |
| 龙头候选输入 | `leader_llm_candidate` 或相关表 | 可选，但需记录状态 |

如果基础数据不满足，阶段一不得继续。

返回：

```json
{
  "status": "failed_precondition",
  "error_code": "BASE_COLLECTION_NOT_READY",
  "missing_tables": ["subject_stock_daily_snapshot", "stock_daily_bar"]
}
```

## 5.4 Step 1：题材周期真源生成

新增正式任务：

```text
theme_cycle_truth
```

职责：

```text
基于已采集的题材、股票快照、事件、行情数据，计算当日题材周期状态。
```

执行子步骤：

```text
1. build_theme_cycle_evidence_daily
2. build_cycle_judgement
3. build_identity
4. build_cycle_judgement
5. build_mainline_state
```

目标产物：

```text
theme_cycle_evidence_daily
theme_cycle_judgement_v2
mainline_identity
mainline_state_daily
```

验收 SQL：

```sql
select count(*)
from theme_cycle_judgement_v2
where trade_date = :trade_date;
```

要求：

```text
rows > 0
```

如果 rows = 0：

```text
theme_cycle_truth 失败
不得进入复盘报告生成
```

## 5.5 Step 2：龙虎榜对象化

任务：

```text
dragon_tiger_object_build
```

职责：

```text
基于已采集的龙虎榜原始数据，构建复盘报告可直接消费的 dragon_tiger_object。
```

目标产物：

```text
dragon_tiger_object
```

验收 SQL：

```sql
select count(*)
from dragon_tiger_object
where trade_date = :trade_date;
```

状态规则：

```text
rows > 0              → success
rows = 0 且确实无榜   → skipped_no_data
rows = 0 但应有数据   → failed_no_rows
```

注意：

```text
runner 的 result.status=ok 不等于任务成功。
必须以目标表写入结果为准。
```

## 5.6 Step 3：资金行为增强

任务：

```text
money_flow_enhanced_build
```

职责：

```text
基于股票快照、行情、资金相关输入，计算个股与题材资金行为。
```

目标产物：

```text
money_flow_enhanced
```

派生产物：

```text
theme_capital_flow
```

其中 `theme_capital_flow` 可以由：

```text
theme_cycle_judgement_v2 + money_flow_enhanced + subject_stock_daily_snapshot
```

派生。

验收 SQL：

```sql
select count(*)
from money_flow_enhanced
where trade_date = :trade_date;
```

要求：

```text
rows > 0
```

如果资金数据确实不可用，可以进入 partial，但必须明确：

```json
{
  "status": "partial",
  "missing_sections": ["money_flow_enhanced"]
}
```

默认不允许静默成功。

## 5.7 Step 4：强势股跟踪池生成

任务：

```text
strong_stock_watch_build
```

职责：

```text
基于题材周期、股票快照、K线结构、资金行为、异动信号和龙头候选，生成强势股分层。
```

目标产物：

```text
strong_stock_watch_pool
strong_stock_watch_history
```

必须修正：

```text
当前 strong_stock_watch 不能再是假成功。
必须真实执行 BuildStrongStockTrackingUseCase，或者从控制台移除。
```

验收 SQL：

```sql
select count(*)
from strong_stock_watch_history
where trade_date = :trade_date;
```

要求：

```text
rows > 0
```

如果 rows = 0：

```text
strong_stock_watch_build 失败
不得生成完整复盘报告
```

## 5.8 Step 5：复盘真源 readiness 检查

新增统一 readiness 检查：

```text
PostMarketDerivedDataReadinessCheck
```

检查项：

| 真源表 | 要求 | 对应复盘栏目 |
| --- | --- | --- |
| `theme_cycle_judgement_v2` | rows > 0 | 主线与支线 / 题材阶段 / 事件分 / 市场分 |
| `money_flow_enhanced` | rows > 0 | 主线资金流入前10 / 资金行为 |
| `strong_stock_watch_history` | rows > 0 | 强势股分层 |
| `dragon_tiger_object` | rows > 0 或 skipped_no_data | 龙虎榜 |
| `subject_stock_daily_snapshot` | rows > 0 | 股票基础事实 |

readiness 通过：

```json
{
  "status": "ready",
  "trade_date": "2026-05-26",
  "derived_tables": {
    "theme_cycle_judgement_v2": 8,
    "money_flow_enhanced": 220,
    "strong_stock_watch_history": 90,
    "dragon_tiger_object": 35,
    "subject_stock_daily_snapshot": 26316
  }
}
```

readiness 不通过：

```json
{
  "status": "failed_precondition",
  "error_code": "POST_MARKET_DERIVED_DATA_NOT_READY",
  "missing_tables": [
    "theme_cycle_judgement_v2",
    "money_flow_enhanced",
    "strong_stock_watch_history"
  ]
}
```

不通过时：

```text
不得进入阶段二
不得写 post_market_recap_snapshot
不得覆盖已有完整快照
```

# 6. 复盘模块阶段二：复盘报告展示

## 6.1 阶段二定位

阶段二才是 read-only。

它负责：

```text
读取阶段一生成的复盘真源表
封装 DailyReview
写入 post_market_recap_snapshot
前端按 5/22 样式展示
```

阶段二不负责：

```text
重新采集外部数据
重新计算题材周期
重新计算强势股分层
重新生成资金行为增强
```

## 6.2 阶段二执行流程

```text
Step 1：读取复盘真源表
Step 2：构造 DailyReview
Step 3：构造 recap_doc
Step 4：构造 report sections
Step 5：写入 post_market_recap_snapshot
Step 6：前端读取 /api/v2/daily-review 展示
```

## 6.3 DailyReview 结构

```ts
interface DailyReview {
  review_date: string
  market_summary: MarketSummary
  theme_reviews: ThemeReview[]
  capital_reviews: CapitalReview[]
  trading_principle: TradingPrinciple
  created_at: string
}
```

## 6.4 theme_reviews 字段要求

为了满足 5/22 页面样式，`theme_reviews` 除文档定义字段外，允许增加展示字段，但不得修改原字段语义：

```ts
interface ThemeReview {
  theme_id: string
  subject_key: string
  theme_name: string
  theme_stage: string
  theme_strength: 'STRONG' | 'MEDIUM' | 'WEAK'
  day_change: number
  event_chain: ThemeEvent[]
  sentiment_judgement: string
  capital_validation: 'CONFIRM' | 'NEUTRAL' | 'DENY'
  leader_stocks: LeaderStockBrief[]

  // 5/22 页面兼容字段
  theme_kline?: string
  event_score?: number
  market_score?: number
  mainline_strength_score?: number
  fade_risk_score?: number
  final_cycle_state?: string
  final_mainline_alive?: boolean
  total_inflow?: number
  leader_inflow?: number
  action_advice?: string
  conclusion?: string
}
```

## 6.5 capital_reviews 字段要求

```ts
interface CapitalReview {
  stock_code: string
  stock_name: string
  net_buy_amount: number
  seat_type: 'INSTITUTION' | 'HOT_MONEY'
  related_theme: string
  ai_comment: string
}
```

来源：

```text
dragon_tiger_object
money_flow_enhanced
```

## 6.6 强势股分层字段要求

用于 5/22 页面：

```ts
interface StrongStockReview {
  stock_code: string
  stock_name: string
  theme_name: string
  role: string
  leader_composite_score: number
  leader_capital_score: number
  trend_strength_score: number
  support_score: number
  position_label: string
  pattern_labels: string[]
  pct_chg: number

  volume_ratio: number
}
```

来源：

```text
strong_stock_watch_history
money_flow_enhanced
stock_kline_judgement
stock_abnormal_signal
leader_candidate
```

# 7. API 设计

## 7.1 采集模块 API

### 启动基础采集任务

```http
POST /api/v2/collection/start
```

请求示例：

```json
{
  "task_key": "daily_collection",
  "trade_date": "2026-05-26"
}
```

职责：只执行基础数据采集任务。不得生成复盘报告。

### 查询采集状态

```http
GET /api/v2/collection/status?job_id=xxx
```

返回：

```json
{
  "status": "success",
  "trade_date": "2026-05-26",
  "base_tables": {
    "subject_stock_daily_snapshot": 26316,
    "stock_daily_bar": 5200,
    "auction_snapshot": 5200,
    "dragon_tiger_raw": 100
  }
}
```

## 7.2 复盘模块 API

### 启动每日动态复盘数据生成

```http
POST /api/v2/post-market/derived-data/generate
```

请求：

```json
{
  "trade_date": "2026-05-26",
  "force": false
}
```

执行：

```text
theme_cycle_truth
dragon_tiger_object_build
money_flow_enhanced_build
strong_stock_watch_build
readiness_check
```

返回：

```json
{
  "status": "success",
  "trade_date": "2026-05-26",
  "derived_tables": {
    "theme_cycle_judgement_v2": 8,
    "dragon_tiger_object": 35,
    "money_flow_enhanced": 220,
    "strong_stock_watch_history": 90
  }
}
```

### 查询每日动态复盘数据 readiness

```http
GET /api/v2/post-market/derived-data/readiness?date=YYYY-MM-DD
```

返回：

```json
{
  "status": "ready",
  "trade_date": "2026-05-26",
  "tables": {
    "subject_stock_daily_snapshot": 26316,
    "theme_cycle_judgement_v2": 8,
    "dragon_tiger_object": 35,
    "money_flow_enhanced": 220,
    "strong_stock_watch_history": 90
  }
}
```

### 生成复盘报告快照

```http
POST /api/v2/post-market/recap/generate
```

职责：只在 readiness ready 后，生成 DailyReview / post_market_recap_snapshot。

返回：

```json
{
  "status": "success",
  "trade_date": "2026-05-26",
  "snapshot_status": "complete"
}
```

如果 readiness 不通过：


# 12. 状态机设计

## 12.1 复盘模块状态

```text

DERIVING
  ↓ readiness ok

RECAP_GENERATING
  ↓ 写入 post_market_recap_snapshot
RECAP_READY
```

如果缺数据：

```text

RECAP_GENERATING → FAILED_PRECONDITION
```

# 13. 错误处理规则

## 13.1 不允许假成功

任何任务如果目标表 rows=0，必须明确状态：

```text
success
skipped_no_data
failed_no_rows
failed_precondition
```

不允许：`status=success` 但目标表为空。

## 13.2 不允许覆盖完整快照

如果 readiness 不通过，不允许写 `post_market_recap_snapshot`，也不允许覆盖上一份完整快照。

## 13.3 partial 规则

只有用户显式选择"允许生成部分复盘"时，才允许写 partial snapshot。

partial 必须在 diagnostics 中明确：

```json
{
  "partial": true,
  "missing_sections": ["dragon_tiger_object"]
}
```

默认不允许 silent partial。

# 17. 最终结论

本次重构的关键不是继续修字段，而是恢复正确系统边界：

```text
采集模块：采集基础数据
复盘模块阶段一：计算每日动态复盘数据
复盘模块阶段二：生成并展示复盘报告
```

只有这样，系统才不会再出现：

```text
控制台全绿，但复盘全空
任务成功，但快照不可用
字段缺失，却覆盖旧报告
```

最终目标：

```text
日采集完成 ≠ 复盘完成
动态数据生成完成 + readiness ready = 可以生成复盘
复盘报告生成完成 = 可以展示
```

这就是新的合约边界。
