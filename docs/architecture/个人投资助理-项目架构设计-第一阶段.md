# 1、系统整体架构设计

本项目的核心是聚合市场热点与新增题材，并提供题材趋势图。一个**结构化、可检索的题材知识库**以及**可视化热度趋势**是关键输出，实现从“事件”到“题材”再到“热度计算”和生命周期管理。提供行业产业链查询、龙头个股选择等功能。完整的题材分析不能止步于抽象概念，最终要**落地到具体的产业链环节和上市公司股票**。通过 AI 大模型生成结构化事件“摘要”和“方向”，实现自动化产生“精华解读”和选股功能。

## 1.1 系统主要核心模块及功能

- **新闻数据抓取模块** `news_crawler_service`：  
  实现对新闻事件的实时获取，新闻数据源被抓取并存入 `news_raw`。

- **模型服务模块** `model_service`：  
  将新闻提炼为结构化的 `news_event`。其中 `impact_industries`（影响行业）字段，是 `theme_service` 进行题材匹配的关键输入之一。

- **数据服务模块** `database_service`：  
  统一 Postgres/Redis 的访问入口，并实现 Redis Stream 总线能力与消费者组框架。

- **题材服务模块** `theme_service`（中枢引擎）：  
  将 `news_event` 与题材数据库匹配，建立并维护一个**题材知识库**（`theme_master`），通过事件频率、置信度、行业关联等计算**实时热度**（`theme_heat`），并判定题材生命周期（`theme_lifecycle`，第一阶段未完成）。  
  - 生成主题映射列表，将事件与主题关系及置信度持久化（`event_theme_map`）。  
  - 实现多维热度算法：基于事件数量、事件置信度、方向、来源权威性、产业链扩散等动态更新热度（第一阶段热度表/算法为规划项）。  
  - 对外提供题材榜/详情/曲线/股票相关题材等接口（第一阶段未完成）。

- **API 提供服务（规划）**：  
  向前端和其他模块暴露主题查询接口和事件主题映射接口（第一阶段未完成）。

# 3、核心理念：从“静态词库”到“动态策略引擎”

可以将**市场噪声（新闻）**转化为**策略信号（题材生命周期）**的处理器，实现三层递进的理解：

- **语义理解层**：理解新闻在说什么（技术突破、政策发布、业绩爆发）。  
- **市场映射层**：判断这件事影响谁（哪个行业、哪条产业链、哪些具体公司）。  
- **策略判断层**：评估这件事的“交易价值”（短期情绪催化 or 长期基本面拐点）。

# 4、系统工作流逻辑

## 4.1 第 1 步：事件结构化（model_service）

- 输入：原始新闻（`news_raw`）  
- 处理：AI 抽取关键信息，生成结构化事件  
- 输出：`news_event`（event_type / summary / impact_industries / direction / confidence）  
- 示例：  
  “Rokid CEO称智能眼镜销量达30万台”  
  → event_type=产品发布；impact_industries=[消费电子, 人工智能]；direction=利好；confidence=0.85

## 4.2 第 2 步：题材发现与匹配（theme_service 核心）

### 任务 1：与题材库匹配 / 新题材创建

- 输入：消费 `stream:events:normal` 与 `stream:events:major`  
- 处理：`ThemeService.discover_theme()`  
- 输出：  
  - 匹配成功：ACK 原消息，更新题材/热度/映射  
  - 匹配失败：  
    - **major**：立即创建新题材  
    - **normal**：写入 `stream:events:pending`，ACK 原消息

### 任务 2：对 pending 事件聚类分析，形成新题材

- 输入：消费 `stream:events:pending`  
- 处理：定期批量聚类：`ThemeService.trigger_clustering_analysis()`  
- 输出：  
  - 形成新簇：创建新题材，重新匹配 pending 事件  
  - 未形成：保持 pending 状态

# 7、数据层架构设计

## 7.1 Stream 定义（全保留）

为了及时响应事件处理，系统应处理的事件流包括：

- 输入流：  
  - `stream:events:major`（重大事件输入）  
  - `stream:events:normal`（普通事件输入）

- 输出流：  
  - `stream:events:pending`（normal 未匹配事件队列）  
  - `stream:events:decision`（决策输出流）  
  - `stream:themes:updates`（题材更新流）  
  - `stream:dead:letter`（死信队列）

| 流名称 | 类型 | 用途 | 消费者组 |
| --- | --- | --- | --- |
| `stream:events:major` | 输入流 | 重大事件输入 | `theme_processors` |
| `stream:events:normal` | 输入流 | 普通事件输入 | `theme_processors` |
| `stream:events:pending` | 输出流 | 未匹配事件队列 | `clustering_workers` |
| `stream:events:decision` | 输出流 | 决策输出流 | `decision_executors` |
| `stream:themes:updates` | 输出流 | 题材更新流 | `update_subscribers` |
| `stream:dead:letter` | 错误流 | 死信队列 | `monitoring` |

# 10、核心模块设计（原文保留）

## 10.1 ThemeProcessor（业务调度中心）

**职责**：

- 监听 major/normal 输入流
- 根据模式调用主题发现
- 生成业务决策
- 发布决策到 decision 流

关键方法（接口示意）：

```python
class ThemeProcessor:
    async def _process_message_classification_first(self, stream_type, stream_name, message_id, message_data): ...
    async def _process_with_category_matched(self, stream_type, stream_name, message_id, event_data, category_result): ...
    async def _process_with_category_failed(self, stream_type, stream_name, message_id, event_data, category_result): ...
    async def _publish_decision(self, decision): ...
```

## 10.2 DecisionExecutor（决策执行器）

**职责**：

- 监听 decision 流
- 执行具体业务操作
- 更新数据库
- 发布结果到 themes:updates 流

决策类型（示例）：

```python
{
    "action": "update_theme",
    "action": "create_new_theme",
    "action": "publish_clustering",
    "action": "clustering_result"
}
```

## 10.3 ClusteringListener（聚类监听器）

**职责**：

- 监听 pending 流
- 执行聚类分析
- 发布聚类结果决策
- 删除已处理消息

处理逻辑（ASCII）：

```
监听 pending -> 收集>=3 -> 聚类分析 -> 发布 clustering_result 决策 -> 删除已处理 pending
```

## 10.4 创建新题材时必须遵守的规则（原文保留）

## 10.5 行业题材（investment）

- 优先匹配 1/2 级 industry 分类；在匹配路径下创建 3 级题材
- 若仅匹配到 1 级 industry，需生成唯一 2 级分类（parent_code 指向 1 级）
- 创建前必须校验：分类编码与名称唯一（不可重复）

## 10.6 概念题材（concept）

- 若未匹配到任何 1/2 级分类：创建 concept 1 级 + 2 级 + 3 级题材
- 若仅匹配到 1 级 concept：生成唯一 2 级 concept，再创建 3 级题材
- 若匹配到 1+2 级 concept：在其路径下创建 3 级题材

## 10.7 组件职责边界

- ThemeProcessor：业务调度与决策生成（不做题材内容生成）
- ThemeRuleBasedGeneratorFixed：题材内容与分类数据生成
- DecisionExecutor：只执行决策并落库（不做业务延伸）
- 三者协议必须一致、简洁、高扩展

## 12. 第一阶段优化目标与验证体系

### 12.1 题材匹配优化方向（重点）

- semantic_matcher：从固定阈值改为**事件级动态阈值**
  - 先计算全量语义分布（如 p95/p98），结合候选数量目标（3~30）自适应
  - 分段策略：Strong / Candidate / Weak
  - 先控候选规模，再做精排（dynamic 阈值与 final_score 解耦）
  - 先灰度再全量：建议 10% 流量 A/B，关注“候选爆炸占比”“漏召回占比”

- 引入 LLM 裁判（Qwen2.5 + llama.cpp）作为最终裁决（必须完成的优化功能）
  - semantic_matcher 粗筛 → LLMThemeArbiter 最终判定
  - 目标：解决“向量相似高但语义不属于同题材”的错配

- 新题材创建逻辑需要优化
  - 创建新题材时的分类推断，可以直接沿用第一次题材分类的匹配结果，不需要再进行分类推断

### 12.2 优化验收目标（以 76 测试集为基准）

- 题材数量收敛到接近 10
- 聚类精度（Clustering Precision）：正确归集事件数 / 总事件数
- 归集完整性（Collection Completeness）：AI 发现事件数 / 实际相关事件数
- 主题分离度（Theme Separation）：1 - (交叉混入事件数 / 总事件数)
- 三方对比：优化系统 vs 基线系统（纯聚类） vs 久赢恒丰标准
- 产出量化测试报告；测试需调用真实 DeepSeek（非模拟）

### 12.3 测试框架与环境注意事项

- 必须在既有框架上验证：`test_theme_processor.py`
- macOS + Python 3.13；transformer 相关测试切换环境：`conda activate theme_matcher_env`
